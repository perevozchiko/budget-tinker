# BudgetTinker — Multi-Currency Functional & Technical Specification

**Status:** Approved product requirements with explicitly labeled engineering design; review revision 2 (2026-10-29)  
**Target branch:** `feature/multi-currency`  
**Language:** English  
**Application:** BudgetTinker, native local-first desktop budgeting application (Rust 2024, eframe/egui, SQLite, serde/JSON)  
**Scope:** First complete release of **manual multi-currency budgeting**  
**Baseline:** The repository's remotely accessible `master` branch was reviewed on 2026-10-29. A remote `feature/multi-currency` branch was not found during that check; inspect the actual working branch before changing code. This specification does not claim that implementation is complete.

### Decision register — authority of requirements

- **APPROVED PRODUCT RULES (must implement):** one immutable base currency chosen at budget creation; 11 built-in currencies; categories/reports/goals in base; one currency per account; account-currency locking after history; explicit frozen operation amounts and FX; manual exchange principal and separate fees; per-month valuation; `Incomplete`/`Estimated`; refunds, splits, debts, budget boundaries, In Transit, historical rate correction/Undo, JSON restore, current-month editing, manual confirmation of scheduled foreign-currency postings, retained optional Frankfurter lookup, and all 12 acceptance directions.
- **ENGINEERING DESIGN (implementation may refine if invariants/tests remain true):** internal Rust type names, field storage representation, monthly close flag encoding, reference rate lookup order, reconciliation decomposition, account-group persistence, caching/index shape, UI layout, transaction subtype names, and report subline naming. Document justified deviations before changing financial semantics.
- **EXPLICITLY DEFERRED:** automatic FX refresh, background network polling, new recurring *cross-currency exchange templates*, bank-file cross-currency pair matching, additional currencies, crypto, cost basis/FIFO/tax reporting, and broad backward compatibility across every pre-release alpha schema.
- **IMPORTANT SCOPE CLARIFICATION:** the owner wants the *currently existing personal budget file to keep opening*. Provide a narrow, safe **current-schema → new-schema** upgrade with backup and rollback. This is not a mandate to maintain every old alpha version. Never overwrite or test using the owner's real files.


## 0. Instructions to the implementation agent

Implement this specification in small, reviewable, testable increments, without replacing the existing product or rewriting unrelated modules. Read `AGENTS.md`, `docs/DEVELOPMENT-PLAN.md`, and `docs/VALIDATION.md` first. Inspect current branch/working tree, keep unrelated modifications, reuse existing model/commands/serde/Undo patterns, and create all tests with synthetic data. Treat this document's **approved decisions** as fixed, and use the **engineering rules** below as the proposed coherent implementation of those decisions; document any conflict with existing behaviors before making a breaking change.

The three priority end-to-end scenarios are: (1) everyday expenses in RSD in a EUR-based budget; (2) exchanging money between the user's own currency accounts, with actual sent/received amounts and explicit fees; and (3) purchases denominated in one currency but charged to an account in another. The first **complete** multi-currency version must also implement refunds, splits, valuation, reports, debts, in-transit transfers, budget-boundary transfers, atomic Undo/Redo, and lossless JSON backup/restore.

## 1. Fixed product rules

**MC-001 — One budget, one base currency.** The user chooses the budget's base currency during initial setup, before writing financial data. Once selected and the budget created, the base currency is permanently immutable in that budget. There is no later Settings conversion of the base currency. Other budgets, if supported, choose independently at creation.

**MC-002 — Exactly 11 built-in fiat currencies:** `EUR`, `USD`, `RSD`, `RUB`, `TRY`, `GBP`, `CHF`, `CAD`, `AUD`, `JPY`, `KWD`. No custom currencies, cryptocurrency, precious metals, or dynamic ISO catalogue. Additional currencies require a later application update. `JPY` has 0 fractional digits, `KWD` has 3, and the others have 2 (use explicit per-currency metadata rather than assumptions scattered through the UI).

**MC-003 — Categories and budget allocations are base-only.** Category balances, monthly allocations, targets, goals, rollover, over-/underspending and `Available to Budget` use only the base currency. No category holds a separate foreign-currency balance. Savings goals are specified solely in base currency; no foreign-currency goals.

**MC-004 — One account, one currency.** A bank's multi-currency product is modeled as separate currency accounts, optionally grouped under an existing account group. A group's total is valued in base currency. An account's currency can be edited only when it has **no financial history**, including no transactions, opening balance record or saved historical balances; a current zero balance does not mean an empty history. For a populated account, create another account and move funds through an explicit transfer; the old account may be archived/closed with its history intact.

**MC-005 — Money and rate precision.** Persist account amounts as signed integer minor units (`i64` subject to checked bounds); use `i128`/checked or exact rational intermediates for multiplication/conversion. Persist exchange rates as exact fixed-point decimals with at least 8 decimal places of precision, retaining the existing 8-decimal scale when sufficient; do not use `f32`/`f64` for authoritative money or FX. Round only at defined currency minor-unit boundaries, consistently and symmetrically for positive/negative amounts. Record exact persisted base equivalents rather than repeatedly recomputing them from displayed rounded rates.

**MC-006 — Unified English numeric format, irrespective of UI language:** `1,234.56 EUR`, `117,000.00 RSD`, `125,000 JPY`, `125.345 KWD`; ISO codes, comma thousands separator, period decimal separator, minus sign for negatives. Input must be validated unambiguously: accept ungrouped decimal `1234.56` and correctly grouped `1,234.56`, reject ambiguous/incorrect grouping (`1,23`) and excess fractional digits; never reinterpret a comma as a decimal separator. Language settings may still localize labels, not money formatting. Also fix the current `parse_fixed()` comma-as-decimal behavior and add grouped-number input tests; ensure `money()` renders grouped values in all locales.

## 2. Two separate FX mechanisms

**MC-010 — Per-operation frozen FX [APPROVED + ENGINEERING DEFAULT].** Every posted non-base-currency operation has a complete, independently stored FX lock: actual account currency/minor amount, signed frozen base equivalent, effective operation FX rate or exact derived ratio, quote date, source, and (optionally) merchant currency/amount. Suggested source types: `Manual`, `BankActual`, `MonthlyDefault` (copied, NOT referenced for revaluation), `FrankfurterAccepted` (explicit user-confirmed suggestion) and `DerivedExact`. For ordinary foreign-currency expense/income, prefill the rate from that transaction month's manually stored rate, otherwise the most recent preceding rate (clearly **Stale / suggested**), but freeze a COPY after the user explicitly confirms the operation. A stale quote is never silently authoritative. Permit editing the suggested rate or entering the exact base equivalent. If neither rate nor base equivalent is available, block posting and offer inline entry without clearing the draft. On base-currency accounts, actual base debit/credit is authoritative; merchant foreign price is metadata. The post must remain valued the same after monthly rate corrections. `MonthlyDefault` is provenance, not a live mutable foreign key.

**MC-011 — Monthly valuation FX [APPROVED].** Store one explicit rate per currency/month where a nonzero month-end account or transit exposure requires it; canonical storage is **base units per one foreign unit**, positive and at least eight fractional decimal digits of precision. EUR-like examples are merely illustrative; actual budget base may be any of the 11. Manual entry is mandatory for offline operation. Preserve **Frankfurter as an optional user-triggered lookup/suggestion button** where already available; network access happens only on deliberate user interaction, never on startup/background, and a returned quote must be displayed (source/date) and explicitly accepted before it becomes a provisional monthly quote or a frozen operation quote. No external key or connection may be required for core functions. No fetched quote ever modifies an existing posted FX lock or historical closed rate without the explicit correction flow.

**MC-012 — Independent histories.** Updates to monthly valuation rates affect only current/historical balance valuations and dependent valuation summaries; they never update a previously posted transaction's frozen account amount, budget equivalent, original purchase amount or frozen transaction quote. Correcting the operation itself is a separate explicit edit subject to reconciliation rules.

**MC-013 — Missing and stale rates [APPROVED].** If an operation needs a conversion and no frozen base equivalent or quote can be established, block posting and allow immediate inline rate entry. When a required monthly valuation rate is missing, mark the month **`Incomplete`**. For preview only, use the latest **earlier** known rate and label the affected figure **`Estimated`**, showing the source rate month/date; do not persist this as final valuation, use it for budget calculations requiring authoritative totals, or silently mark the month complete. If no earlier rate is available, show `Unavailable` rather than an invented value. The month becomes complete when all rates required for its final balances (including in-transit exposure) are available. Zero exposure does not require an otherwise-unused monthly rate.

**MC-014 — Current/open and historical monthly rate editing [APPROVED].** The current month's rate is a **provisional valuation** while the month is open and may be edited freely; each edit updates provisional valuation and correctly invalidates cached totals, but never posted FX locks. A rate present for every required exposure makes the current month calculable (`Provisional`, not `Incomplete`), even though it is not a final month-end quote. Missing rate means `Incomplete`; the last earlier rate may provide a separately labeled `Estimated` preview only. Month finalization is an explicit user action available after month end and after required quotes are provided; do not silently close a month by calendar rollover. For any previous month or finalized month, changing its rate requires an explicit correction workflow with before/after preview for Net Worth, budget valuation, Revaluation, adjacent-period reports, audit history, atomic Undo/Redo, and no mutation of frozen posted transactions. This introduces an explicit month/rate lifecycle and a correction command; current `add_snapshot()` rejects replacement and must be refactored. If historical months cannot be finalized in the current UI, their rates still use the historical correction flow.

## 3. Financial operations

**MC-020 — Standard expense/income.** The signed account amount is denominated in the account's currency. The budget/category impact is the explicitly persisted signed base equivalent. For foreign accounts, calculate an initial base amount from the chosen operation rate but allow an exact manual override; store the result and its origin. Realized account movement and category activity must never be inferred from merchant price alone. Record the transaction date as the primary date and month for budgeting; optional `posted_date` stores the actual bank settlement date and does not automatically change booking month, FX or account amount.

**MC-021 — Cross-currency purchase.** Store separately: (a) merchant currency and merchant amount (e.g. `10.00 EUR`); (b) actual account posting (e.g. `-1,180.00 RSD`); and (c) frozen base budget equivalent (e.g. `-10.09 EUR`), plus FX metadata. The merchant amount is informative and not another account posting. The list row displays **only** the actual signed account amount; details reveal all three values, rate, rate date and source.

**MC-022 — Returns/refunds [APPROVED + ENGINEERING ALLOCATION RULE].** A refund is a distinct **positive actual receipt**, posted to the selected receiving account (which may differ from the purchase account or currency) with its **own** independently frozen base equivalent and quote. Link it to the source purchase (and to specific source split IDs if applicable). It is not earned Income. Partial refunds are allowed; the form allocates refunded base amounts to the original purchase categories, and a refund of a split purchase requires an explicit allocation across its original categories with deterministic rounding. Category reversals cannot cumulatively exceed the original category's charged frozen base amount unless the user explicitly records an unrelated correction. **A refund's frozen base value MAY exceed the original purchase's base cost** due to FX: restore the category only up to its original net charged base amount; put any positive excess in a distinct non-Income `FX Refund Adjustment` subline within FX results, preserving the entire actual receipt and reconciliation identities. Do not silently cap the actual incoming account balance, do not alter the original purchase, and never book the excess as earned Income. If a refund is less than the purchase in base terms, the residual category expense remains. Multiple refunds must not over-restore category spending. Protect reconciled linked entries.

**MC-023 — Split transactions.** Every split part has an amount in the **account currency**, a category (or permitted transfer metadata under the existing split rules), and an independently stored frozen base equivalent that can be manually corrected. The signed sum of all parts' account amounts must equal the parent account amount **exactly in minor units**. The signed sum of part base equivalents must equal the parent frozen base amount **exactly in base minor units**. Deterministic remainder allocation is required for computed splits, and a user override must be rebalanced/validated explicitly; preserve zero-net reallocations and never put rounding remainder onto a zero-amount part merely by accident. No mixed merchant-currency split parts in v1.

**MC-024 — Same-currency transfers.** Keep current linked paired-transfer behavior. For a genuine same-currency transfer between owned accounts, posted amounts are equal and opposite except for an explicitly separate fee; it does not create Income or Expense by itself. Respect the budget boundary if on-budget/off-budget status differs.

**MC-025 — Cross-currency exchange.** User enters **actual positive sent and received amounts** in the two account currencies (e.g. send `100.00 EUR`, receive `11,650.00 RSD`). The displayed effective rate is derived from these amounts; it is not the authoritative input. Never infer the bank's actual received amount from a monthly quote. Link both postings to a single logical exchange record/command, preserve both currency amounts, locked base valuations and applied fee(s).

**MC-026 — Exchange fee [APPROVED + ENGINEERING INPUT RULE].** Model any explicit fee as a separate linked expense with actual account debit, paying account, actual debit currency, posted date, category and independently frozen base equivalent. The payer may be a **third account in a third currency**. Fee is additional to sent principal by default; if the bank debited one inclusive amount, user must split principal and fee without duplicating the debit. If the **quoted/merchant fee currency differs from the payer-account currency**, collect *both* quoted fee amount/currency (metadata) and actual charged amount in payer-account currency (authoritative posting), plus its own locked conversion to budget base. This is a cross-currency fee purchase, **not** an automatic second debit from an imaginary currency account. Show effective principal exchange rate excluding fees and total cost including fees. Fee date is the date of actual bank debit (sending or receiving, independently selectable), not implicitly the exchange completion date. Failure to supply a required frozen fee equivalent blocks completion with inline correction.

**MC-027 — Frozen exchange difference, not tax-lot P/L [APPROVED + ENGINEERING FORMULA].** For a completed exchange, freeze a **reference quote at exchange confirmation** independent of mutable monthly valuations, defaulting to that month's manually entered quote (or last preceding rate as a **visibly stale suggestion**) but always editable/explicitly confirmable. Freeze principal-side signed base equivalents `P_send_base < 0` and `P_receive_base > 0`. Define `ExchangeDifference_base = P_send_base + P_receive_base` for that completed exchange; equal-valued transfers produce 0. For a simple base→foreign exchange with a frozen reference quote `q` (base per foreign unit), `P_receive_base = round_to_base_minor(received_foreign × q)`; the sending base is the actual outflow. For foreign→foreign, both signed legs require independent frozen base equivalents; do not infer one from mutable snapshots later. The derived **bank rate** = actual received units / actual sent units, shown informationally. The *reference quote* may be different from the bank rate and is the fixed basis for Exchange Difference. Monthly rate corrections NEVER change this FX difference; any valuation consequence is in Currency Revaluation. Fees and extra FX adjustments appear in separate expense/non-Income lines, not hidden inside this difference. No FIFO, acquisition lots or tax-profit accounting.

**MC-028 — Budget boundary.** On-budget → on-budget transfer is category-neutral (apart from explicit fees / valuation effects). On-budget → off-budget transfer requires an expense category and reduces Available to Budget at its frozen base amount. Off-budget → on-budget increases Available to Budget as funds introduced into the budget; label this separately or as a non-earned inflow, not automatically wages/income. Off-budget → off-budget does not affect the spendable budget. All accounts, including off-budget and debts, participate in all-accounts Net Worth. Preserve correct categorization for foreign-to-foreign and foreign-to-base transfers.

**MC-029 — In-transit transfers [APPROVED + ENGINEERING FAILURE POLICY].** A multi-day exchange has one stable logical ID, `sent_date`, expected/actual `received_date` and states such as `InTransit`, `Completed`, `Failed`, `Reversed`. On send, debit source and credit an *internal* transit asset in source currency, never a user-visible account; include the transit asset **once** in Net Worth and in eligible budget value when appropriate. On receipt, debit the transit asset and post actual received destination units using frozen reference values/confirmed fees; support date/month boundary. Do not book a forecast receipt as a completed posting. Before completion, `Cancel/Failed` cannot simply delete the source debit or fabricate a refund: record an **actual** return to the source or other receiving account (which may be less than sent), freeze its FX, book actual fees/FX adjustment, and clear transit exposure when settlement is confirmed; until then funds remain a traceable unresolved claim/exposure. A completed transfer may only be reversed via an explicit linked correction with reconciliation checks, not silent deletion. Any reversal is one atomic command with audit trail. Fee occurs on its **actual debit date**, at send or receipt, whichever the real bank movement indicates. Budget boundary is crossed at send for on-budget→off-budget and at confirmed receipt for off-budget→on-budget; on-budget→on-budget stays eligible while in transit. Exact settlement dates and visibility must be tested.

**MC-030 — Negative balances and debt.** Allow signed/negative native-currency balances, including a USD liability that becomes more negative in EUR when USD appreciates. Net Worth uses month-end valuations and includes liabilities regardless of budget status. Available to Budget must respect existing `on_budget`, `account_type`, credit/debt reserve and overspending logic; **do not** universally subtract every off-budget liability from spendable funds. Currency revaluation of off-budget debt changes Net Worth but not Available to Budget merely because the debt exists. Preserve account close/archive rules and debt category semantics.

**MC-031 — Scheduled transactions [APPROVED].** Existing same-currency schedules continue to work. When posting any scheduled transaction on a foreign-currency account in a base-currency budget, **require explicit manual confirmation** of actual account amount, FX quote or exact base equivalent, and any actual fee before the posting becomes real; never post an estimated schedule automatically with a carried-forward FX quote. The template may store its native account amount and show a labeled indicative base preview, but the confirmed posting creates a new frozen FX record. Scheduled split/budget allocations use the same invariant. New *recurring cross-currency exchange templates* remain deferred; their future design is fixed sent amount plus actual receipt/fee confirmation.

## 4. Valuation, budget calculations, reports

**MC-040 — Reporting currency [APPROVED].** All reports use the fixed base currency. Original account and merchant amounts are in transaction details.

**MC-041 — Net Worth [APPROVED].** For month `m`, `NW_all(m) = Σ_a convert(native_balance_a(m), month_rate(currency_a,m)) + Σ_t convert(native_transit_t(m), month_rate(currency_t,m))`, with separate signed debt valuations and consistent base-minor rounding. Each native balance is derived from actual ledger movements, never merchant prices, and internal transfer postings net correctly. Unpriced exposures mark totals `Incomplete`; `Estimated` previews are non-authoritative. The same calculation restricted to eligible on-budget assets/transit drives `B(m)`, subject to account-type/credit rules. `NW_all` also includes off-budget accounts/debt; budget boundaries do not reduce total NW merely by moving owned value.

**MC-042 — Income/Expense [APPROVED].** `EarnedIncome(m)` and `CategoryExpense(m)` are sums of **frozen account-to-base financial flows** explicitly classified as income and spending, respectively. Refunds offset their linked spending categories; explicit fees are expenses. Show boundary inflows as their own class. Own-account transfers, Exchange Difference, FX Refund Adjustment, and Currency Revaluation are NOT earned income. Do NOT infer earned income as a Net Worth residual.

**MC-043 — Currency Revaluation: formal residual identity [ENGINEERING DESIGN enforcing APPROVED separation].** For each reporting population (all accounts for Net Worth; eligible on-budget assets for budget value), let `F(m)` be the signed total of every **actual base-frozen balance-changing posting** occurring during month `m` (including income, expenses, explicit fees, both transfer legs and internal transit leg postings, refunds, and debt principal changes; exclude informational merchant amounts and unposted forecasts). Each linked posting contributes once. Then define:

`Reval_all(m) = NW_all(m) - NW_all(m-1) - F_all(m)`.

`Reval_budget(m) = B(m) - B(m-1) - F_budget(m)`.

The two are distinct because off-budget exposures and budget boundaries differ. `F` includes an exchange's signed principal-side frozen values, so **its `ExchangeDifference` is already part of `F`** and must NOT be subtracted again from the residual. For presentation, decompose `F_all(m)` into `EarnedIncome - Expenses + BoundaryNet_all(=0 for same-valued internal moves) + ExchangeDifference + FXRefundAdjustment + other clearly named actual flows`. Grouping must be a **partition** of locked postings, not a second posting. There may be rounding cents in Revaluation because the stock (valued rounded balances) and frozen flow values are rounded at defined boundaries. Those cents belong in the explicit Revaluation/rounding explanation; do not invent earned Income or silently alter a category.

- **Ledger bridge invariant:** `NW_all(m) - NW_all(m-1) = F_all(m) + Reval_all(m)` exactly in base minor units for every complete month; classify `F` into named reporting components and assert reconciliation to the cent.
- **Envelope bridge invariant:** Define `A(m) = B(m) - Deferred(m) - Σ CategoryBalance_i(m) - OtherExplicitReserves(m)` under existing credit/debt and overspending semantics. Then `ΔA = ΔB - ΔDeferred - ΣΔCategoryBalance - ΔOtherExplicitReserves` exactly. `ΔB = F_budget + Reval_budget`; report `F_budget` via income, boundary inflows/outflows, category spending, FX differences, fees and other explicit budget flows. **Do not write a simplistic `ΔAvailable = Income - Expenses + FX` formula** without subtracting movements in funded category balances: when a categorized expense reduces both cash and its category reserve, it often leaves unallocated Available unchanged. Any unexplained residual is a bug, never `Income`.
- For the first available month, define/opening valuation baseline explicitly; do not compare to an invented previous-month zero unless opening balance is a posted opening flow. If either comparison month is incomplete, do not report a final revaluation delta. Include in-transit exposures in `NW`, `B`, and corresponding frozen `F` at sending/settlement as appropriate.

**MC-044 — Budget arithmetic and FX disclosure [APPROVED].** Use the ledger and envelope bridges above, with distinct `Exchange Difference`, `FX Refund Adjustment`, `Currency Revaluation` and fee expenses. On-budget eligible FX effects can alter available funds; off-budget valuation only changes all-accounts Net Worth, never Available directly. Preserve existing overspending rules and credit card/debt categories, and do not double count any transfer or FX adjustment. When a corrected monthly quote changes NW, dependent Revaluation compensates while posted frozen Exchange Difference stays constant. Historical rate-edit preview shows both old/new bridge decompositions.

**MC-045 — Compact account and transaction UI.** In `All Accounts`, display each account's **native balance only** in its row. Details reveal its base equivalent, monthly rate/date and status. Group totals and overall total are in base currency (with `Incomplete`/`Estimated` indicators if needed). In a transaction list, display only the actual signed amount in its account currency. Clicking/opening details shows original merchant amount and currency, account amount, frozen base equivalent, FX rate/date/source, and linked exchange/refund metadata. Preserve compact YNAB-4-like ergonomics and existing grouping/reorder behavior; avoid columns with duplicate values.

## 5. Recommended model and storage changes

The following is a **logical schema**, not a command to introduce these precise Rust names. Keep established types and integration boundaries when reasonable.

```
CurrencyCode      // restricted to the 11 approved fiat codes
Money { minor: i64, currency: CurrencyCode }
LockedFx {
    base_minor: i64,            // immutable until explicitly editing the operation
    base_currency: CurrencyCode,
    rate_scaled_or_ratio: ExactQuote,  // 8+ decimals / exact rational
    quote_date: YYYY-MM-DD,
    source: Manual | BankActual | MonthlyDefault | FrankfurterAccepted | DerivedExact,
    source_month_or_id: Option<...>, // provenance ONLY; never mutable valuation dependency
    manually_overridden: bool,
}
Transaction {
    ...existing fields...
    account_minor: i64,
    transaction_date: YYYY-MM-DD,
    posted_date: Option<YYYY-MM-DD>,
    merchant_purchase: Option<Money>,
    locked_fx: LockedFx,
    refund_of: Option<TransactionId>,
    refund_split_links: Vec<SplitId>,
    split_parts: Vec<SplitPart>,
    exchange_group_id: Option<ExchangeId>,
}
SplitPart { id, account_minor: i64, base_minor: i64, ...existing metadata... }
MonthlyRate { currency, month, rate_scaled, rate_date, source, revision ... }
MonthLifecycle { month, is_closed_or_finalized, ... } // if required by actual UI
Exchange {
    id, source_account, destination_account, sent_minor, received_minor?,
    sent_date, expected_receive_date?, actual_receive_date?,
    status: InTransit | Completed | Failed | Reversed,
    frozen_reference_fx: LockedFx/ReferenceQuote,
    linked_principal_posting_ids, fee_posting_ids, transit_posting_ids,
}
FxRefundAdjustment { refund_id, base_minor, ... } // semantic classification; may be derived
HistoricalRateChange { month, currency, old_rate, new_rate, time, ... }
``` 

**Rate direction rule:** internally rates are base-per-foreign. The UI must clearly label both directions; it may prefer the human-friendly `1 BASE = X FOREIGN` entry and display the inverse `1 FOREIGN = Y BASE` in details. Never silently invert with lossy floating-point arithmetic. Store sufficient precision and the exact confirmed base amount. This direction choice is an ENGINEERING UX DEFAULT, not a separately owner-approved policy.

Mandatory implementation constraints:

1. Avoid two competing authoritative values. Account posting amount is authoritative for its account; persisted `base_minor` is authoritative for budget activity; month-end snapshot is authoritative for valuation. Merchant amount is informational; derived rate is informative unless it was used to initially create the frozen equivalent.
2. Cross-reference all linked postings by stable IDs; never infer transfer/refund associations from matching amount/date alone. A transfer and its optional fee(s) form one logical command and Undo unit.
3. A frozen operation must remain valid after a monthly rate correction. Replace the current validator's dependence on recomputing transaction base values from mutable `Snapshot` records with validation of frozen operation invariants. Historical monthly snapshots may be mutable only through the explicit correction flow.
4. Preserve existing reconciliation flags, register import state, payee rules, hidden categories, scheduled transactions and existing reports. An edit/delete touching any reconciled linked posting must be blocked unless the user explicitly unreconciles all affected postings through a supported workflow.
5. Add `TRY` and all metadata centrally; make account creation select an account currency, not force `Budget.base`; surface inline FX entry when a required rate is missing.
6. **Narrow current-budget upgrade (OWNER CONFIRMED).** Preserve the ability to open the owner's current pre-feature `.budgettinker` budget file. Implement a one-time current-schema → new-schema converter with a recoverable SQLite-safe backup, preflight validation, explicit confirmation, atomic replacement/rollback, and clear failure message. Do not require multi-version compatibility for older alpha histories or backward editing with the old app. Test synthetic copies of current-schema documents; never exercise migration on the personal live file. Keep serde defaults when they make *semantically correct* sense, but do not default missing FX locks to invented values.
7. Persist operation revisions and command-level Undo/Redo coherently. Plan index/cache design **before** implementation for 100k events: avoid repeated full-scan `activity()` for every month/category, repeated full-history `balance()` per account, and O(month × category × transaction) report recomputation. Build month/account/category aggregates or memoized time-bucket summaries with deterministic invalidation on rate edits, transfers, Undo and restore. Retain whole-document SQLite revisions only if repeatable measured save/Undo benchmarks meet agreed responsive targets; otherwise use more granular indexed storage/command logs. Do not introduce speculative unrelated rewrites.
8. Validate on every save and import: valid currency and minor precision; IDs and links; complete transfer/exchange state; account type semantics; dates; rate > 0; matching split sums; frozen base invariants; missing-rate policy; checked overflow; no duplicate transaction identity.

## 6. Commands and atomicity

Define or extend explicit domain commands rather than mutating disparate UI collections independently. At minimum cover: `CreateBudget(base)`, `CreateAccount(currency)`, `ChangeEmptyAccountCurrency`, `PostTransactionWithFx`, `PostSplitWithFx`, `PostRefund`, `PostExchangeWithFee`, `SendTransfer`, `CompleteTransfer`, `FailOrReverseTransit`, `UpdateOpenMonthRate`, `FinalizeMonth`, `CorrectHistoricalMonthlyRate`, `PostBoundaryTransfer`, `ConfirmScheduledForeignPosting`, `AcceptFrankfurterSuggestion`, `UpgradeCurrentBudgetFormat`, `ExportJson`, `RestoreJson`.

Each command: (a) validates its complete proposed effect; (b) prepares changes on a candidate model or DB transaction; (c) checks all links/money invariants and reconciliation restrictions; (d) persists atomically; and (e) produces **one** Undo/Redo action. On failure, change **nothing**. Undo of exchange restores both sides, associated fee, locked quote and every derived budget effect. Undo of a historical rate correction restores all affected valuation results atomically; it must not alter posted transactions.

**JSON restore is a document-replacement operation, NOT an ordinary Undo item**: it clears/reinitializes the Undo/Redo stack after success and must never leave stale commands pointing to previous object IDs. An import is a whole-budget replacement, not a merge: deserialize and validate the entire incoming JSON before touching current data; create a **recoverable automatic backup** of the live current budget using a safe SQLite backup/export method (never blindly copy a live WAL file), clearly warn, get explicit confirmation, then replace atomically. If anything fails, preserve/recover the prior budget. Verify full export → import → export semantic equality; include all supported financial and linking fields. No bank-file multi-currency auto-match extension is required; **existing CSV/QIF/OFX/QFX/legacy importers must be audited and preserved**. For every imported transaction, determine account currency from the chosen account, parse the actual account posting, and use any explicit imported merchant/base amount only as provenance until validated. If a valid frozen FX cannot be obtained, stage that row as **Pending FX** inside an import preview, offer manual quote/base entry, and forbid final posting of unresolved rows. User may explicitly skip rows or cancel the entire import. Never silently equate merchant amount with charged amount, use monthly snapshots as live references, or drop foreign-currency fields. Tests cover previously supported single-currency files and new foreign-account rows. Newly automated cross-bank exchange pairing remains out of scope.

## 7. UI requirements

- Account creation/edit: currency picker; edit currency only for accounts with no history. Preserve group membership, ordering, archive and account type.
- Monthly FX editor: currency/month, clearly labeled forward/inverse quote, eight-or-more-decimal rate entry, date, source, explicit provisional/current vs finalized/historical status; open-current-month immediate edits; close/finalize action after month end; stale-rate `Estimated` preview; historical correction with exact before/after impact preview and Undo. Optional **Look up rate (Frankfurter)** button makes network request only on click and asks before accepting the returned quote.

- Exchange editor: source/destination accounts, actual sent/received amounts, **separate frozen, editable reference quote** vs derived bank rate, fee paying account/currency and actual charge amount, optional different quoted fee currency, actual fee date, optional different send/receive dates; In Transit/Complete/Failed/Reversed, cancellation and confirmation controls; total debit and net destination preview.

## 8. Numeric acceptance examples (all rates fictitious)

**AC-01 — Transaction with merchant/account/base divergence:** Budget base EUR. Merchant charges `10.00 EUR`; RSD account is debited `1,180.00 RSD`; user confirms frozen budget expense `10.09 EUR`. Account balance decreases by 1,180.00 RSD; Groceries activity decreases by 10.09 EUR; details show all three amounts; future monthly FX edits do not change the expense.

**AC-02 — Partial refund:** The same RSD account receives `1,150.00 RSD` later; **user manually chooses/overrides** `9.89 EUR` as the refund's base equivalent (not necessarily proportional to the purchase exchange rate). Net account movement from purchase/refund is `-30.00 RSD`; net Groceries expense is `0.20 EUR`; earned Income remains 0. Both entries and FX locks remain distinct and linked.

**AC-03 — Exchange and additional fee:** Send `100.00 EUR` from EUR checking; receive `11,650.00 RSD` on RSD checking; additional fee `1.00 EUR` from EUR checking, categorized as Bank Fees. Actual EUR account reduction = `101.00 EUR`; RSD account increase = `11,650.00 RSD`. Derived rate = `116.50 RSD per EUR`. User explicitly confirms a **frozen exchange reference** of `0.00855000 EUR/RSD`; acquired RSD is recorded at `99.61 EUR`, so **frozen** Exchange Difference is `-0.39 EUR` and the separate fee expense is `1.00 EUR`. The monthly rate may initially suggest this reference but is NOT used as a live dependency. Assuming the month-end RSD valuation is **also** `0.00855000`, the value change is `-1.39 EUR`, **not** Income and not double-booked as Revaluation. If the month-end rate is later corrected, this Exchange Difference stays `-0.39 EUR` and Revaluation absorbs the difference (e.g., at final `0.00900000`, the RSD is worth `104.85 EUR`, so additional Revaluation is `+5.24 EUR`, and total change after fee = `+3.85 EUR`).

**AC-04 — Simple revaluation:** A stable on-budget positive `1,000.00 USD` balance is valued at `0.90000000 EUR/USD` in September and `0.95000000 EUR/USD` in October. Net Worth changes `900.00 → 950.00 EUR`; `Currency Revaluation` is `+50.00 EUR`; earned Income = 0; the eligible on-budget revaluation increases Available to Budget by 50.00 EUR, subject to account type/debt rules. The corresponding off-budget holding changes Net Worth but not Available to Budget.

**AC-05 — Debt revaluation:** A liability holds `-1,000.00 USD`. Rates `0.90 → 0.95 EUR/USD` change valuation from `-900.00 → -950.00 EUR`, reducing Net Worth by 50.00 EUR. Do not automatically charge off-budget debt appreciation to Available to Budget.

**AC-06 — In transit across months:** Source EUR account sends `100.00 EUR` on October 30; no receipt by October 31; on November 2, destination receives a confirmed `11,650.00 RSD`. On October 31, the 100 EUR transit asset appears in Net Worth **once**, even though the source bank account is already down 100 EUR. After November 2 it is replaced by the actual RSD balance and does not remain counted. Settlement/exchange result uses confirmed amounts.

**AC-07 — Budget boundary:** Move `100.00 EUR` from an on-budget account to an off-budget account and assign category `Investments`. Available to Budget decreases by 100 EUR; Net Worth does not drop by 100 EUR merely because the money moved to another owned account. Moving funds back increases available funds but is not automatically earned wages.

**AC-08 — Missing monthly rate:** A nonzero RSD balance exists at month end but the RSD month-end quote is missing. Mark month `Incomplete`. Show an estimated base conversion using the last earlier rate with its month/date, or `Unavailable`; never present the estimated total as final. A new RSD expense can still be posted **only** with its own frozen valid quote/base equivalent.

**AC-09 — Rate correction:** Correct a historical RSD monthly quote and preview affected Net Worth, revaluation and spendable valuation for impacted periods. Confirm atomically; undo restores old valuations; previously posted transaction's `base_minor`, category activity, merchant amount and frozen quote are identical before/after.

**AC-10 — Split precision:** Account transaction `-1,180.00 RSD` split into `-708.00 RSD` Groceries and `-472.00 RSD` Household; frozen base parent `-10.09 EUR`; valid part base values (example) `-6.05 EUR` and `-4.04 EUR`. Exactly `-1,180.00 RSD` and `-10.09 EUR` in respective sum checks. No hidden rounding cent.

**AC-11 — Native currency decimals:** `125,000 JPY` stores integer minor 125000 (0 decimals). `125.345 KWD` stores integer minor 125345 (3 decimals); invalid extra fractional digit is rejected. Test negative amounts and overflow.

**AC-12 — Full JSON round-trip:** A synthetic budget with all 11 currencies, positive/negative balances, historical FX changes, linked split/refund/exchange/in-transit states, monthly quotes, account groups, reconciled flags, categories and history exports to JSON; validated restore into an isolated fresh budget produces the same canonical financial state, IDs and amounts, not duplicates.

**AC-13 — Account immutability:** Account with historic transaction now at 0 cannot change currency. A truly empty account can; a new account plus exchange remains the supported path.

**AC-14 — Full atomic undo:** Undoing the AC-03 exchange removes/restores both principal postings, the fee expense and connected budget adjustments as a unit; no intermediate broken state is persisted. Undoing AC-09 restores valuation corrections without rewriting transaction locks.

**AC-15 — Frozen FX under monthly correction:** Book AC-03 with frozen reference `0.00855000`. Correct the RSD month-end rate from `0.00855000` to `0.00900000`. Expected: frozen Exchange Difference remains `-0.39 EUR`; month-end RSD value becomes `104.85 EUR`; monthly Revaluation changes by `+5.24 EUR`; account transactions, category fees and base postings unchanged. Ledger and envelope bridges reconcile to the cent, before and after Undo.

**AC-16 — Open-month edit and missing quote:** In October, with nonzero RSD exposure and no October quote, show `Incomplete` and any older-rate preview as `Estimated`. Enter October rate; state becomes `Provisional`. Edit again while October is open; revalue preview without modifying posted FX. Finalize only after month end. Editing September requires historical preview, audit, and Undo. No automatic close.

**AC-17 — Imported foreign-account row and scheduled posting:** Existing CSV/QIF/OFX importer maps an actual debit of `-2,340.00 RSD` into an RSD account in a EUR budget; no valid rate -> `Pending FX`, cannot finalize until quote/base is accepted. Scheduled foreign-account debit remains unposted until the user confirms actual amount and quote; skip/cancel remains safe. Legacy single-currency fixtures still pass.

**AC-18 — Split refund and excess FX:** Original purchase charged `-10.00 EUR` in Groceries and `-5.00 EUR` in Household. Refund receives actual frozen `+16.00 EUR` and is allocated back to source split IDs. Category credits are capped at `+10.00` and `+5.00`; the remaining `+1.00 EUR` is `FX Refund Adjustment`, not earned Income and not an overfunded category. A separate test refunds into a different-currency account at its actual posted amount.

**AC-19 — Third-currency fee and failed transit:** Cross-currency exchange fee is quoted in USD but the bank debits an actual `-200.00 RSD` from a third RSD account. Exactly one RSD account posting is made for the fee, with its independently frozen base value. A transfer failing after month-end continues to show transit exposure until an actual bank refund/settlement is recorded; no phantom credit or double-counting; fee booked on actual bank date.

**AC-20 — Existing-budget safety and JSON restore:** Upgrade a synthetic current-schema `.budgettinker` using SQLite-safe backup; validate links and frozen amounts before commit, verify successful reopen and a deliberate malformed-case rollback. A JSON restore replaces all state, makes its own backup, and **resets Undo/Redo**; Undo cannot resurrect stale pre-restore records. Do not test on the personal budget.

**AC-21 — FX quote direction:** User enters an explicitly labeled market convention such as `1 EUR = 117.00 RSD`, while engine stores a precise consistent base-per-foreign representation. Verify conversion/rounding, quote inversion, bank rate vs frozen reference quote, and a manual exact base override; neither notation silently changes a frozen base amount.

**AC-22 — Both bridges:** For synthetic multi-month budgets with refunds, off-budget transfers, credits, in-transit assets, FX trades, and explicit fees, assert `ΔNW_all = F_all + Reval_all` and `ΔAvailable = ΔB - ΔDeferred - ΣΔCategoryBalance - ΔOtherExplicitReserves` exactly for complete months; verify grouped reported components partition `F` without duplication. Test both current rate changes and historical correction/Undo, including half-cent rounding scenarios.
